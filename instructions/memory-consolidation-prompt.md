# 外部メモリー定期整理プロンプト

GitHubリポジトリ `-リポジトリー名-` の `AGENTS.md`、`memory/index.md`、`knowledge/workflows/external-memory-consolidation.md` を確認してください。

`memory/` は利用者・対象環境固有の永続メモリーを保存する Open Knowledge Format（OKF）v0.2 Bundle、`knowledge/` は固有の現在状態を越えて再利用できる一般化知識を保存する別のOKF v0.2 Bundleとして扱ってください。

この整理処理では、Gitのcommit履歴を過去状態の追跡手段として利用し、リポジトリ本体には現在および今後の利用に必要な情報を優先して残してください。

## Memoryの確認

最近追加された `memory/events/` だけでなく、最近変更された `memory/state/` も確認してください。

関連するStateが現在の正確な原本になっているか確認してください。

特に以下の情報について、現在の状態が正しく反映されているか確認します。

- 採用中の計画・カリキュラム
- 現在の進捗
- 次回開始点
- 数値・在庫などの現在値
- 順序
- 評価軸・判断基準
- 所有状況
- 構成・設定
- 採用中の設計
- 制約・方針
- 完了・未完了状態

確定している情報を、要約のために不要に一般化・省略しないでください。

不明な情報は推測で補完しないでください。

## State / Eventの整理

頻繁に変わる現在値や細かな進捗・試行については、`Memory State` を直接更新してください。

`Memory Event` は、後から状態遷移として独立して参照する価値が高い節目だけにしてください。

Event候補の例:

- 計画・カリキュラム変更
- Stage・工程完了
- 採用案・却下案の確定
- 重要な測定・検証
- 大きな進捗
- 設計・運用方針変更
- 現在Stateがそうなった理由を後から理解するために重要な変化

細かな変更をすべてEvent化しないでください。

細かな変更履歴や過去のStateはGit履歴から確認できるため、現在Stateに不要な履歴情報をStateへ蓄積し続けないでください。

既存Eventについても、独立した履歴文書として残す価値が低く、現在StateやKnowledgeへ十分統合済みであり、Git履歴から追跡可能な場合は、統合・整理・削除を検討してください。

ただし、重要な設計判断、検証結果、節目など、単独で参照する価値が残っているEventは保持してください。

## OKF形式

Memory Conceptを作成・更新する場合は、OKF形式を維持してください。

`index.md`、`log.md` などの予約ファイルを除くMarkdownには、空でない `type` を持つYAML Frontmatterを設定してください。

原則として:

- State: `type: Memory State`
- Event: `type: Memory Event`
- 用途に応じた適切な `scope`
- 関連する `domain`

を保持してください。

既存文書にproducer-defined fieldなどの独自Frontmatterが存在する場合、不要に削除しないでください。

## Knowledgeへの一般化

Memoryの整理後、利用者・対象環境固有の現在状態を除いても、別の会話・作業で長期的に再利用できる新しい知見が明確になったか確認してください。

対象となる例:

- 一般化可能な原則
- 再利用可能な手順
- 設計上の知見
- 検証結果
- 失敗原因と回避策
- 再利用可能な判断基準

新しい再利用知識が明確になった場合だけ、`knowledge/workflows/knowledge-capture.md` に従って整理してください。

新規Conceptを作成する前に、既存Conceptへ統合できないか必ず確認してください。

同じテーマについて複数のKnowledge Conceptが存在し、内容が重複・分散している場合は、可能な限り代表となるConceptへ統合してください。

古いKnowledgeが新しいKnowledgeによって完全に置き換えられており、独立して保持する価値がない場合は、Git履歴で過去状態を追跡できることを前提に、統合後の削除を検討してください。

固有の現在状態そのものを無理にKnowledgeへ一般化しないでください。

Knowledgeへ一般化したことを理由に、現在利用中のMemory Stateを削除しないでください。

## リポジトリの統合・肥大化防止

Git履歴を変更履歴の原本として利用できるため、Markdownファイル側へ過去の全状態を残すことを目的にしないでください。

定期整理では、情報を追加するだけでなく、積極的に統合・整理してください。

特に以下を確認します。

- 同じ内容を持つStateが複数存在していないか
- 同一テーマのKnowledgeが複数ファイルへ不必要に分散していないか
- 現在Stateへ統合済みの古い情報が残り続けていないか
- Eventが細かな変更履歴の置き場になっていないか
- supersededなKnowledgeが現行Knowledgeと併存していないか
- indexに不要・重複・削除済みの項目が残っていないか
- logがGit履歴と同じ変更内容を過剰に重複記録していないか

整理の優先順位は原則として次の通りです。

```text
重複した内容を既存Conceptへ統合
    ↓
現在Stateを最新状態へ集約
    ↓
不要になった重複・旧文書を削除
    ↓
index / logを現在構成へ合わせる
```

Git履歴から十分追跡できる細かな過去情報を、リポジトリ本体へ永久に残す必要はありません。

ただし、単純にファイル数を減らすことを目的に、現在の判断や再開に必要な情報まで削除しないでください。

判断基準は、

「この情報を現在のファイルから削除しても、今後の作業継続・判断・知識再利用に支障がなく、必要ならGit履歴から過去状態を確認できるか」

とします。

YESなら統合・削除を積極的に検討してください。

## Index / Logの整理

Conceptを統合・削除・移動した場合は、関連する `index.md` も同時に更新してください。

Indexは現在存在し、現在利用するConceptを指す状態に保ってください。

`log.md` はGitのcommit履歴を複製するためのものとして扱わないでください。

Bundle全体に関わる重要な構造変更や、後から一目で把握する価値がある変更だけを記録してください。

細かなファイル更新履歴はGitへ委ねて構いません。

## 更新判断

新しい情報がなく、既存Stateも現在の正確な状態で、Knowledgeへ追加・統合すべき内容もなく、整理すべき重複もない場合はGitHubを変更しないでください。

変更のための変更は行わないでください。

既存文書を更新するときは、現在の内容を確認した上で、新しい情報との差分を整理し、必要最小限の変更を行ってください。

ただし、複数ファイルの統合や不要文書の削除によって全体を単純化できる場合は、単一ファイルへの小さな追記を繰り返すより、整合性のある統合を優先してください。

## 実行結果

処理完了後は、実際に行った変更だけを簡潔に報告してください。

例:

- 更新したMemory State
- 統合・削除したMemory Event
- 統合・追加・削除したKnowledge
- 更新したindex / log
- 重複整理
- 変更なし

削除や統合を行った場合は、何をどこへ統合したか分かるように報告してください。

実際に変更していない内容を、変更済みとして報告しないでください。

## GitHub書き込み失敗時

GitHubへの変更が、安全チェック、権限制約、競合、その他の理由で拒否された場合は、無理に回避しないでください。

安全チェック回避を目的とした表現変更、難読化、別経路による書き込みなどは行わないでください。

変更できなかった場合は、必ず以下を報告してください。

- 変更できなかったこと
- 拒否・失敗した理由
- 対象ファイル
- 変更しようとした内容
- 確認できた現在State
- 発見した不足・古い情報・重複・不整合
- 未反映のまま残っている情報

失敗した処理を保存完了として扱わないでください。

自動実行内で無理に再試行せず、利用者が通常の会話・操作から改めて変更を指示できる状態で終了してください。
