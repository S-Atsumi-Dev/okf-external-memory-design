# リポジトリを維持するためのルール

外部メモリーは、情報を追加し続けるだけでは扱いにくくなります。

長期運用では、現在値の更新、重複の統合、不要情報の除去まで含めて維持します。

## 残す情報を選ぶ

保存候補になるのは、次回以降の作業に影響する情報です。

例えば:

- 現在の作業位置
- 採用済みの設定や判断
- 継続して使う制約
- 繰り返し利用できる手順
- 検証で確定した結果

一方、会話中だけ意味を持つ内容や、将来の判断に影響しない細部は残しません。

## 現在値は上書きしてよい

Stateは履歴帳ではありません。

数値、設定、進捗などが変わった場合は、古い値を本文へ残し続けず、現在値へ更新します。

過去の版が必要になった場合はGit履歴を利用します。

## Eventを増やしすぎない

Eventは、後から単独で参照する意味がある変化だけに限定します。

Event化しやすいもの:

- 大きな工程の完了
- 採用方針の変更
- 重要な検証の完了
- 大きな構成変更

Event化しなくてよいもの:

- 小さな数値更新
- 一時的な試行
- 通常の進捗
- 単純なState修正

## Knowledgeは集約する

似た内容のKnowledgeが複数存在する場合は、既存文書へ統合します。

新しいファイルを作る前に、次を確認します。

- 同じテーマの文書がないか
- 既存手順の追記で表現できないか
- 既存Conceptの更新で足りないか

Git履歴で旧版を確認できるため、置き換え済みの文書を現在のツリーへ残し続ける必要はありません。

## Indexを現在構成に合わせる

ファイルを追加・移動・統合・削除した場合は、関連Indexも更新します。

Indexから存在しない文書を参照したり、同じ内容への入口が複数できたりしないようにします。

## 保存対象外

以下は外部メモリーへ保存しません。

- パスワード
- APIキー
- アクセストークン
- 秘密鍵
- 回復コード
- Cookie・セッション情報
- 不要な機微情報
- 生の会話全文
- 根拠のない推測
- 保存権限のない第三者・組織の情報

## 矛盾が見つかった場合

Stateと新しい情報が食い違っている場合は、古いStateを機械的に維持しません。

実際の対象、一次情報、現在のユーザー入力など、より適切な情報源を確認した上でStateを修正します。

重要な方針変更であれば、必要に応じてEventも残します。

## 定期的な整理

定期処理では「何を追加するか」だけでなく、次を確認します。

- 古いStateが残っていないか
- 重複文書がないか
- Eventが増えすぎていないか
- Knowledgeが分散していないか
- Indexが現在のファイル構成と一致しているか
- Git履歴と同じ内容をlogへ重複記録していないか

変更する必要がなければ、更新は行いません。
