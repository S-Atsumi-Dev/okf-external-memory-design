# 設計上のトレードオフ

外部メモリーは、情報を多く保存すれば良くなる仕組みではありません。

継続性、検索しやすさ、更新コストのバランスを取る必要があります。

## 現在状態を短距離で取得できること

長い会話履歴が残っていても、次回必要なのが最後に確定した状態だけである場合があります。

そのため、現在値を集約したStateを持つことで、再開時に必要な探索量を減らせます。

一方でStateを短くしすぎると、判断基準や制約が失われます。

「短いこと」ではなく「その文書だけで再開できること」を優先します。

## 履歴をどこまで残すか

Stateへ過去経緯を積み上げると、現在有効な情報が分かりにくくなります。

反対に、すべての変化をEventとして残すとファイル数が増えます。

そこで、

- 現在有効な情報はState
- 独立した意味を持つ節目はEvent
- ファイルの細かな変化はGit

という3つの役割に分けます。

## 保存量と検索性

情報を残す量が増えるほど、必要な情報へ到達する仕組みが重要になります。

全ファイルを毎回モデルへ渡す方式では、Context消費とノイズが増えます。

Indexやdomain単位の分割を使い、必要な文書だけ取得できる構造にしておく方が扱いやすくなります。

## Markdown + Gitの利点

OKFをMarkdownで保持すると、通常のGit運用をそのまま利用できます。

- 差分確認
- 過去版の参照
- ロールバック
- Review
- Branchによる変更分離

このため、外部メモリー専用の履歴機構を別途作らなくても、多くの変更管理をGitへ委ねられます。

## 自由度と一貫性

OKFは文書構造に自由度があります。

これは対象ごとに必要な項目を追加しやすい一方で、ルールがなければ書き方がばらつく原因にもなります。

そのため、形式そのものよりも、

- StateとEventの使い分け
- 既存文書への統合
- Indexの維持
- 不明値を推測しない
- 保存対象を選別する

といった運用規則が重要になります。

## 外部メモリーだけを信用しない

外部メモリーには、過去時点の情報や誤った記録が残る可能性があります。

実コード、実設定、公式仕様など、より直接的な情報源がある場合は、それらを優先します。

外部メモリーは、継続作業を補助するための情報層として扱います。

## 規模が大きくなった場合

ファイル数や更新頻度が増えると、Git + Markdownだけでは検索や同時更新が不足する可能性があります。

その場合でも、State / Event / Knowledgeの役割分離は維持しつつ、検索Index、DB、RAG、権限制御などを別レイヤーとして追加できます。

保存形式と検索・実行機構を分離しておくことで、後から構成を拡張しやすくなります。
