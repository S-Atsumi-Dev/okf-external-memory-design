# 情報の配置と役割

この方式では、長く残したい情報を1種類の文書へ集めず、用途ごとに置き場所を分けます。

## Repository Layout

```text
repository/
├─ memory/
│  ├─ state/
│  └─ events/
│
└─ knowledge/
   ├─ concepts/
   ├─ workflows/
   ├─ tools/
   ├─ references/
   ├─ experiments/
   └─ decisions/
```

`memory/` と `knowledge/` はそれぞれ独立したOKF Bundleです。

## memory/

`memory/` には、特定の利用者・対象・継続テーマに結びつく情報を置きます。

### state/

継続作業で「今どうなっているか」を確認するための文書です。

保持する内容の例:

- 現在位置
- 採用中の設定
- 数値や在庫
- 制約
- 未完了事項
- 次に行うこと

同じdomainについて複数の現在状態を並立させるのではなく、基本的には1つの文書へ集約します。

### events/

後から単独で振り返る意味がある変化だけを残します。

例えば、工程完了、方針変更、重要な検証結果などです。

細かな変更までEventへ分解すると文書数が増えるため、通常の値更新はStateだけを書き換えます。

## knowledge/

`knowledge/` には、特定の現在状態から切り離しても使える内容を置きます。

例えば:

- 説明可能な概念
- 再利用できる手順
- ツール固有の注意点
- 検証で得られた知見
- 設計上の判断と理由

同じテーマの文書が既にある場合は、新しいファイルを増やすより既存文書へ統合します。

## 情報ごとの優先先

情報の種類によって、確認すべき場所を分けます。

| 情報 | 優先して確認する場所 |
|---|---|
| 現在の進捗・設定 | `memory/state/` |
| 重要な節目 | `memory/events/` |
| 再利用可能な知識 | `knowledge/` |
| 実際のコード | 対象コードリポジトリ |
| 実際の設定値 | 対象システム |
| 外部サービスの最新仕様 | 公式情報 |

外部メモリーだけを万能な原本にせず、情報の性質に応じて確認先を切り替えます。

## Indexの役割

ファイル数が増えても、最初から全内容をモデルへ渡す必要はありません。

```text
index.md
   ↓
対象カテゴリ / domain
   ↓
必要な文書
```

各Indexは、保存場所の一覧だけでなく、必要な情報へ到達するための案内として使います。

これにより、保持する情報量とモデルへ渡す情報量を分離できます。
